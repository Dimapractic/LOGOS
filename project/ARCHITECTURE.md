# Архитектура и проектные решения

## Организация интеграции

Используется оркестрация: Hub управляет порядком команд, ERP/WMS/TMS выполняют свои локальные операции. Общей базы между сервисами нет. Каждый сервис принимает HTTP/JSON и открывает только собственный файл SQLite.

Для небольшого учебного стенда состояние каждого сервиса хранится одной JSON-записью в таблице `state`. Изменения выполняются под `BEGIN IMMEDIATE`; фиксация результата команды, её ключа идемпотентности и бизнес-изменений атомарна. Это сознательное упрощение схемы, а не рекомендация для больших систем.

## Прохождение заказа

1. Интерфейс генерирует UUID заказа и передаёт его Hub, который создаёт заказ в ERP.
2. ERP сохраняет заказ со статусом `new`. Endpoint `/outbox` выдаёт такие заказы до подтверждения плана.
3. Hub добавляет заказ в свою устойчивую очередь. Кроме немедленного добавления он опрашивает ERP каждую секунду: сбой между записью в ERP и записью в Hub не теряет заказ.
4. Hub отправляет WMS команду `reserve`, TMS — `book`, ERP — `plan`.
5. По модельному времени последовательно выполняются WMS `ready`, WMS `consume`, TMS `depart`, TMS `arrive`, ERP `complete`.
6. В Hub остаются план, фактические времена, журнал попыток и данные каждой отправленной команды.

В этой реализации `/outbox` — упрощённая выдача из самой таблицы заказов, а не отдельный брокер сообщений. Пока заказ остаётся `new`, повторный импорт не создаёт новую задачу: Hub проверяет UUID.

## План «точно в срок»

Пусть `W` — начало окна доставки, `P` — сборка, `L` — погрузка, `T` — перевозка, `B` — временной резерв.

```text
Плановая передача = W
Плановое прибытие = W − B
Плановое отправление = W − T − B
Плановая готовность склада / подача машины = W − T − B − L
Плановое начало сборки = W − T − B − L − P
```

Резервирование возможно заранее. Готовность склада наступает не раньше плановой готовности и не раньше фактического резерва плюс время сборки. Отправление возможно после готовности и длительности погрузки. Прибытие — после фактического отправления и длительности дороги. До начала окна получатель ожидает; передача раньше окна не выполняется.

Фактическое время передачи фиксируется при формировании команды подтверждения в ERP. Если её ответ потерян, повтор сохраняет исходное время, поскольку сама передача уже произошла в модели. Успешное завершение интеграции может быть позже из-за повторов.

Проверка соблюдения окна: `window_start ≤ delivered_at ≤ window_end`. Если заказ создан слишком поздно, он не отклоняется автоматически: прогноз показывает риск опоздания. Параметры транспортировки фиксированы, внешние дорожные данные не используются.

## SLA и тайм-аут

| Система | Норматив успешного ответа | Тайм-аут HTTP-попытки |
|---|---:|---:|
| ERP | 1 с | 3 с |
| WMS | 2 с | 5 с |
| TMS | 2 с | 5 с |

Значения учебные, заданы в `POLICY` в `services/hub.py`. При ответе TMS за 2,5 с операция успешна, но SLA нарушен. После 5 с без ответа инициируется обработка тайм-аута.

Время измеряется `perf_counter()` вокруг HTTP-запроса, включает ожидание ответа и получение тела. Для журнала используются реальные UTC timestamp; модельные часы не влияют на измерение. Доля соблюдения SLA = успешные ответы в пределах норматива / все попытки команд. HTTP-ошибки учитываются как несоблюдение SLA. Опрос состояния и `/outbox` не входит в эту метрику.

Журнал попыток сохраняется целиком, интерфейс показывает последние 200. В записи каждой команды также хранятся реальные `started_at` / `finished_at`, позволяющие вычислить общую длительность логической операции с ожиданием повторов. Отдельная визуализация этой длительности пока не сделана.

## Повторы и идемпотентность

Временные ошибки: сеть/тайм-аут и HTTP 408, 429, 500, 502, 503, 504. Максимум четыре попытки в одном цикле, backoff 2/4/8 секунд с jitter 0–0,3 с. HTTP 409, 422 и другие постоянные ошибки сразу переводят операцию в `dead`. Это бизнес-решение стенда: например, отсутствие машины требует решения человека.

Перед отправкой сохраняются тело команды и ключ `order_id:stage`. После перезапуска используются те же данные. В принимающей системе ключ, хеш тела, ответ и изменение состояния записываются одной транзакцией. Одинаковый ключ с другим телом вызывает 409. Один заказ имеет не больше одного резерва и одной перевозки.

Доставка команд — **at least once**. Идемпотентность обеспечивает однократный бизнес-эффект в границах реализованных операций; «exactly once» для сети не заявляется. После четырёх неудач операция остаётся в durable-списке `dead`, аналогичном карантину / DLQ. Ручной повтор запускает новый цикл того же шага и сохраняет его ключ. Журнал прежних попыток остаётся.

Имитация потери подтверждения: сервис сначала фиксирует команду, затем вместо успешного ответа возвращает 504. Это воспроизводит ситуацию неопределённого результата для клиента; физическое обрывание TCP не используется. Настройка задержки свыше тайм-аута позволяет дополнительно проверить настоящий клиентский тайм-аут.

## Компенсация

Отмена доступна до шага отгрузки `load`. Hub сохраняет новую последовательность: `cancel_tms → cancel_wms → cancel_erp`. Она тоже проходит через механизм повторов и восстанавливается после рестарта. WMS возвращает резерв в доступные остатки один раз. После отмены сохраняется запрет новых команд по этому заказу — это защищает от запоздалого исходного запроса.

Отмена недоступна, когда началась попытка списания/отгрузки: неизвестный результат такой операции требует отдельного процесса возврата. Процесс возврата в MVP не реализован. Компенсация запускается пользователем, а не автоматически при каждой временной ошибке.

## API

Полные схемы запросов и OpenAPI доступны на `/docs` у каждого сервиса.

| Endpoint | Назначение |
|---|---|
| Hub `GET /api/state` | Сводка, показатели, последние попытки и снимки систем |
| Hub `POST /api/orders` | Создание заказа через ERP |
| Hub `POST /api/clock` | Запуск/пауза и скорость модельных часов |
| Hub `POST /api/fault/{service}` | Настройки имитации сбоев |
| Hub `POST /api/jobs/{id}/retry` | Повтор остановленного шага |
| Hub `POST /api/jobs/{id}/cancel` | Запуск компенсации до отгрузки |
| ERP `POST /orders` | Сохранение заказа с уникальным UUID |
| ERP `GET /outbox` | Не подтверждённые интеграцией заказы |
| Все имитаторы `POST /commands` | Идемпотентная бизнес-команда |
| Все имитаторы `GET /snapshot` | Состояние для демонстрации |
| Все сервисы `GET /health` | Проверка доступности |

`POST /commands` требует заголовок `Idempotency-Key`. Тело: `action`, `order_id`, `data`. Для бронирования `data` содержит `pickup` и `window_end` (Unix timestamp); для резерва — полный заказ.

## Ограничения и развитие

- Один активный worker Hub; сервис запускается одним процессом. Нельзя запускать несколько экземпляров Hub с одной БД: распределённая блокировка не реализована.
- Worker отправляет команды последовательно. Медленный сервис может задержать обработку других заказов. Для учебного масштаба это допустимо; следующий шаг — отдельные очереди, ограниченный параллелизм и leases.
- В очереди/журнале нет TTL и архивирования. JSON-хранилище удобно для изучения, но не для высокой нагрузки. Для роста — нормализованные таблицы PostgreSQL.
- Пять машин и проверки пересечения плановых интервалов. Нет динамического перепланирования конфликтов из-за фактического опоздания, учёта грузоподъёмности и обратного рейса.
- В заказе одна товарная позиция; единицы — штуки. Нет многоскладской логистики, разделения заказа и частичной отгрузки.
- Готовность/погрузка/прибытие — модельные события. Физические датчики, водители и внешние системы не подключены.
- Нет OAuth, TLS, ролей, распределённой трассировки и промышленной защиты API; локальная привязка ограничивает доступ компьютером пользователя.
- Нет брокера сообщений и circuit breaker. Эти компоненты можно добавить позже, если потребует объём проекта.

Следующая практическая итерация: несколько строк заказа → настройки SLA в интерфейсе → экспорт журнала CSV → адаптер внешней ERP → контейнеры и CI. Текущая версия уже демонстрирует заявленную тему без этих расширений.
